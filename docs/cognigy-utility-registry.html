Supabase Query Tool

needs setup

blocked on: an encrypted Connection

A reusable httpRequest-based tool for reading (or later, writing) Adullam's existing Supabase project — verse lookups, saved plans, session logs.

▸ how to build it
  1. Open the Aquila project → Build → Flows → Aquila Flow, and add a new tool (or ask me to scaffold one) with an HTTP Request node inside its branch.
  2. Set the URL to https://<project-ref>.supabase.co/rest/v1/<table>, method GET (or POST/PATCH for writes).
  3. In the node's Authentication section, pick an API-Key method and click the + next to Parameters to open New Connection. Paste in the service role key there — this is the step that encrypts it instead of storing it in plain text.
  4. Give the Connection a clear name, e.g. Supabase Service Role, and save.
  5. Set a Storage Options context key, e.g. supabaseResult.
  6. Send me the Connection's reference ID and I'll wire the rest of the tool (params, pre/post-process code) to it.
Supabase's gateway expects a header literally named apikey. Cognigy's built-in API-Key auth types produce Authorization: ApiKey … or a fixed X-API-Key header — neither is an exact match. After wiring the Connection, check the actual outgoing request in the Interaction Panel's Debug Mode against a live call; if Supabase returns "No API key found", that's the header name to fix.

Salesforce Case / Handover

needs setup

Escalates a conversation to a human agent queue in Salesforce, with the transcript and structured context attached.

▸ how to build it
  1. Use the Salesforce MIAW connector, not the legacy Chat/LiveAgent one — Salesforce retires that Feb 14, 2026.
  2. In Salesforce Setup: enable Omni-Channel, then create a Service Channel (Salesforce Object = Messaging Session).
  3. Create a Queue, add your human agents as members, and add Messaging User / Messaging Session / Chat Session as supported objects.
  4. Create an Omni-Channel Flow that routes work to that queue.
  5. Create a Messaging Channel (type: Messaging for In-App and Web), routing type Omni-Flow, pointed at the flow above with the queue as fallback. Activate it.
  6. In Cognigy: Build → Handover Providers → + New Handover Provider → Salesforce, and fill in the identifiers Salesforce gives you for the channel.
  7. Add a Handover to Human Agent node to whichever tool should trigger escalation, select this provider, and configure Pre-chat Entities/transcript-on-handover.
Deferred per your call — exploratory only, no org yet. Steps above are ready whenever that changes.

Webhook Router

needs setup

blocked on: a bare Flow + a Webhook Endpoint

One inbound URL for every future external trigger — a dispatcher that routes by payload, not a new endpoint per integration.

▸ how to build it
  1. Build → Flows → + New Flow, name it e.g. Webhook Router — no AI Agent Job node needed, this is a plain dispatch flow.
  2. After Start, add a Lookup (switch) node keyed on a discriminator in the payload, e.g. input.data.event_type.
  3. Wire each case to its handler — inline nodes for simple cases, or an Execute Flow node (available in the GUI's node palette) to jump into a dedicated handler flow and return.
  4. At the end of each case, add an HTTP Request node that POSTs the result to input.data.callbackUrl — read dynamically from the incoming payload, so one router serves many different callers instead of one fixed callback.
  5. Deploy → Endpoints → + New Endpoint, type Webhook, select this flow, set Authentication Method to API Key, and generate a key.
  6. Hand external callers the Endpoint URL and the key (sent as x-cognigy-endpoint-key).
Bonus, free once the Endpoint exists: /inject/{URLToken} and /notify/{URLToken} push a message into an already-running session or straight to a user, without a full round trip.

01 · integration

Generic API-Caller Tool Template

Not a single tool — a shape you duplicate for every new external API, so the auth/error/response wiring only gets solved once.

Right now, every integration this project needs (Supabase, a future client CRM, anything) means wiring an HTTP Request node from scratch: which auth type, how to unwrap the response, what to show the LLM on failure. Building this template first means every tool after it is a five-minute copy, not a fresh design.

  1. Create the tool. In the Aquila AI Agent's Job configuration, add a new Tool. Name it after the capability, not the API — e.g. check_order_status, never call_api. One tool per business capability keeps the LLM's tool list meaningful; a single do-everything "API tool" forces the LLM to guess arguments it can't know.
  2. Add a Code node first, "Prepare Request." Anything you need to compute before the call — normalizing a phone number, building a query string — happens here, writing into input or context. Keep the HTTP node's own fields simple CognigyScript references to what this step already prepared.
  3. Add an HTTP Request node. Set the URL with CognigyScript for dynamic segments, e.g. https://api.example.com/v1/accounts/{{input.aiAgent.toolArgs.accountId}} — tool-call arguments always live at input.aiAgent.toolArgs.<param>, never input.data. In the node's Authentication section, pick the auth type the API needs and use the + next to Parameters to create a Connection — this is what keeps the secret encrypted instead of sitting in plain text in the flow.
  4. Turn on error logging. In the HTTP node's Error Handling section, choose "Log the error with the server response and the URL" — you want this the first time something breaks, not after.
  5. Add an ifThenElse right after the HTTP node, condition input.httprequest.statusCode >= 300. The wrapped response is an object { result, statusCode, length }, never the raw body — this is the most common reason an HTTP tool "fires successfully but returns nothing useful," so always read through input.httprequest.result, never assume the top-level object is the API's JSON. 
    // Then branch — friendly failure, no raw error to the LLM
input.result = "I couldn't reach that service right now. Let's try again in a moment.";

// Else branch — shape the success response
const data = input.httprequest.result;
input.result = `Found it: ${data.status}, last updated ${data.updatedAt}.`;
  6. Resolve Tool Action. Set its answer field to {{input.result}} — never the raw JSON.stringify(input.httprequest) default, which dumps the whole wrapper object at the LLM.
  7. Test it. Open the Interaction Panel, turn on Debug Mode, and send a message that should trigger the tool. Debug Mode shows you the exact outgoing request and incoming response — this is how you catch a wrong header name before a user does.
Test checklist: does the tool fire on the right phrasing, does a deliberately-wrong ID produce the friendly failure branch (not a raw error), and does Debug Mode show the auth header you expect?

02 · accounts

Customer / Account Lookup Tool

Resolves "who is this" against an account record — the first step before anything account-specific happens.

This is deliberately not authentication. It answers "is there an account matching what they told me," not "are they allowed to see it" — that's ID&V's job, built separately, and chained after this one. Keeping them separate means you can look someone up to greet them by name without that alone unlocking anything sensitive.

  1. Create the tool lookup_account, description: "Looks up the caller's account by email or account number. Call this before answering any account-specific question, but this alone does not verify identity." That last clause in the description matters — it's what stops the LLM from treating a successful lookup as permission to act.
  2. Add one parameter, JSON Schema: {"type":"object","properties":{"identifier":{"type":"string","description":"email address or account number the user gave"}},"required":["identifier"]}.
  3. Add an HTTP Request node using the API-caller template from #01 — for now this can point at a stub/mock endpoint, or, once the Supabase Connection exists, a GET against the Supabase REST endpoint filtering by email or account number.
  4. Add a Code node, "Interpret Result." On a match, set context.accountId, context.accountName, and explicitly context.verified = false — writing this explicitly, even though it's the default, makes the ID&V gate impossible to miss when you build it next to this. On no match, set a plain "I couldn't find an account matching that" result.
  5. Resolve Tool Action with the interpreted result.
  6. Add one line to the agent's instructions: "Before answering an account-specific question, call lookup_account if you don't already have context.accountId for this session. A successful lookup identifies the account — it does not by itself authorize account changes."
Chain it with ID&V: any tool that changes data or reveals sensitive details should check context.verified === true first, not just context.accountId being set.

03 · compliance

Consent / Opt-in Capture Tool

Asks explicit yes/no before anything personal gets stored — once per session, in one place, so "what counts as consent here" has exactly one definition.

This reuses the exact channel-gated xApp pattern already proven in verse_of_the_day — a card on webchat, a spoken question on voice — because consent has to be explicit on both, not just implied by continuing to talk.

  1. Create the tool capture_consent, description: "Asks the user for explicit consent before storing any personal information. Call this once per session, before the first tool that saves user data."
  2. Add an ifThenElse on input.channel === "webchat3", same gate used for every xApp tool in this project — voice has no card surface, so it needs its own path.
  3. Then branch (webchat): initAppSession → showXAppAdaptiveCard with a short, specific consent statement (name exactly what you'll store and why) and two Action.Submit buttons, waitForInput: true, contextKey: "consent".
  4. Else branch (voice/REST): a Question node, type yesNo, asking the same thing aloud — consent has to be spoken explicitly here too, not assumed from the caller staying on the line.
  5. Add a Code node after both branches: context.consentGiven = true|false; context.consentAt = new Date().toISOString();
  6. Resolve Tool Action reporting whether consent was given, so the agent can respond appropriately either way.
  7. Gate every data-writing tool. At the top of any tool that saves personal data, add an ifThenElse: context.consentGiven === true — if false, the response asks for consent first instead of proceeding.
Word the consent statement for the specific thing you're about to store — a generic "is that okay?" doesn't hold up as informed consent if a client ever asks how this was captured.

04 · compliance

Audit / Compliance Log Tool

A structured who-did-what-when record for every sensitive action — the thing enterprise clients ask for by name during a security review.

Before building a custom tool, check whether the built-in path already covers it: the AI Agent Job node has a loggingWebhookUrl field that ships request/response data to a URL you control. For simple "log everything" needs, filling that in is less work than a new tool. Build the dedicated tool below when you need to log specific business events (a completed account change, a consent decision) rather than every raw turn.

  1. Pick the sink first. A Supabase table (needs the Connection from the registry above), or a webhook URL (the same pattern the Webhook Router uses to call back out) — decide before building so the tool's HTTP node has somewhere real to point.
  2. Create the tool log_audit_event, parameters: {"type":"object","properties":{"action":{"type":"string"},"details":{"type":"object"}},"required":["action"]}.
  3. Add a Code node, "Build Record." 
    const record = {
  ts: new Date().toISOString(),
  sessionId: input.sessionId,
  accountId: context.accountId || null,
  action: input.aiAgent.toolArgs.action,
  details: input.aiAgent.toolArgs.details || {},
};
context.lastAuditRecord = record;
  4. Add an HTTP Request node POSTing context.lastAuditRecord as the JSON body to the sink from step 1.
  5. Resolve Tool Action with a short confirmation only — never echo the full record back, or the agent may end up narrating internal logging to the user.
  6. Wire it in by instruction, not by chaining. There's no call-and-return node available here, so other tools can't invoke this one directly — instead, add a line to the agent's instructions: "After a successful account change, call log_audit_event with action and a short details object." The LLM sequences the two tool calls itself.

05 · reliability

Rate-Limit / Abuse Guard

A per-session counter that caps a runaway or abused tool before it reaches a downstream API — a pattern added to existing tools, not a new standalone one.

Different tools warrant different limits — a verse lookup can be called often and cheaply; a tool that changes account data or calls a metered client API should be rare. That's why this lives per-tool, not as one global gate.

  1. Open the tool you want to guard (an existing one, or a new one worth protecting from the start — anything that calls a paid/rate-limited downstream API is a good candidate).
  2. Add a Code node at the very top of its branch, before anything else runs: 
    context.callCounts = context.callCounts || {};
const key = "check_order_status"; // this tool's name
context.callCounts[key] = (context.callCounts[key] || 0) + 1;
  3. Add an ifThenElse right after: context.callCounts["check_order_status"] > 5 — pick a limit that fits the tool, not one number reused everywhere.
  4. Then branch: set input.result to a firm, polite decline ("Let's slow down for a moment — try again shortly") and skip straight to Resolve Tool Action, bypassing the tool's real logic entirely for this turn.
  5. Else branch: the tool's normal logic continues unchanged.
  6. Optional: add a reset. Store context.callCounts_resetAt alongside the counts, and clear the whole map when Date.now() - context.callCounts_resetAt passes some window, so the limit is per time-window, not per entire session.
This guards against loops and abuse within one session's context — it isn't a substitute for real rate-limiting on a shared/multi-tenant deployment, which needs to live at the Endpoint or API-gateway layer instead.

06 · localization

Multi-Language / Locale Router

Sets the conversation's language early so later tools and responses can honor it, instead of the agent re-guessing every turn.

Check the built-in path first: the AI Agent's own Speaking Style settings include a Language Configuration toggle that already handles automatic detection and consistent response language. Build the tool below only when other tools — not just the reply text — need to branch on locale (choosing a translation set, a different terms-of-use string, and so on).

  1. Check Speaking Style first. In the AI Agent's configuration, confirm Language Configuration is set the way you want — if the only need is "reply in the user's language," this may be the whole solution.
  2. If downstream tools need it too, create set_locale, parameters: {"type":"object","properties":{"locale":{"type":"string","description":"BCP-47 locale, e.g. en-US, es-ES"}},"required":["locale"]}.
  3. Add a Code node: context.locale = input.aiAgent.toolArgs.locale;
  4. Resolve Tool Action confirming the locale was set.
  5. Chain it with session start. Add it to the same first-turn instruction that triggers bootstrap_session, so locale gets set once, early, rather than the LLM deciding to call it mid-conversation.
  6. Any tool that needs to branch on language reads context.locale directly in an ifThenElse — no need to re-detect it each time.

07 · ops

Health-Check / Status Tool

One callable check confirming every downstream integration is actually reachable — exactly what would have shortened today's Azure OpenAI connection debugging.

This session's own troubleshooting is the working example: confirming Adullam's /health endpoint and its /mcp/sse endpoint both worked, independently of the Cognigy-side LLM connection, is exactly what isolated where the real problem was. A tool like this turns that manual process into one callable check.

  1. Create the tool check_integration_health, description: "Checks whether the Bible retrieval service and connected APIs are reachable. Call this only when explicitly asked to check system status — never as part of an ordinary question."
  2. Add one HTTP Request node per integration worth checking — start with Adullam's own health endpoint: GET https://adullum.onrender.com/health, storage key healthAdullam.
  3. Add more as they exist — a Supabase reachability check, a future client API's own health endpoint — each its own HTTP node, its own context key.
  4. Add a Code node, "Summarize": 
    const checks = [
  { name: "Adullam API", ok: context.healthAdullam?.statusCode === 200 || context.healthAdullam?.status === "ok" },
  // add one line per integration checked above
];
input.result = checks
  .map(c => `${c.name}: ${c.ok ? "reachable" : "NOT reachable"}`)
  .join(". ");
  5. Resolve Tool Action with the summary.
  6. Restrict when it fires. The description's "only when explicitly asked" line matters — without it, the LLM may call a health check speculatively when a real question simply fails, muddying what actually broke.
Once the Webhook Router exists, an external monitor can hit it on a schedule and have it call this tool internally — turning an on-demand check into automated uptime monitoring.

08 · multi-tenant

Client Feature-Flag Tool

Lets one agent serve several client/account contexts with different enabled tools, instead of forking the flow per client.

If this agent (or a package-exported copy of it, see #10) ever serves more than one client, some tools will be right for one and wrong for another. A flag check is far cheaper to maintain than a separate flow per client.

  1. Decide where flags live, for now. Until the Supabase Connection exists, hardcode a small lookup table in a Code node keyed by client/account identifier — swap it for a real Supabase row later without changing anything downstream.
  2. Create the tool load_client_config — or fold this directly into bootstrap_session if it should always run at session start.
  3. Add a Code node: 
    const configs: Record = {
  default: { followUpPicker: true, readingPlans: false },
  // "acme-corp": { followUpPicker: true, readingPlans: true },
};
const clientId = context.clientId || "default";
context.features = configs[clientId] || configs.default;
  4. Resolve Tool Action confirming which config loaded.
  5. Gate optional tools. At the top of any tool that's optional per client (e.g. show_followups for a client who doesn't want the picker UI), add an ifThenElse on context.features.followUpPicker === true before doing anything else.

09 · integration

Custom Extension

For logic a Code node can't handle cleanly — HMAC/JWT-signed requests, or any node you want installed once and reused across many tools and projects.

A Code node's logic can only be reused by copy-pasting it into every tool that needs it. An Extension is a real installable node — write the signing logic once, and it shows up in the Flow editor's palette everywhere, the same way httpRequest or code do.

  1. Prerequisite: a Node.js/TypeScript environment and familiarity with npm — this is the one component here that's real software development, not flow configuration.
  2. Scaffold it with the Cognigy CLI (npm install -g @cognigy/cognigy-cli, then its extension-generator command), which lays out a package.json and an extension descriptor.
  3. Define the node's fields the same way any node has a config schema (label, type, default), and write its execute function — this is where the HMAC-signing or JWT logic actually lives.
  4. Respect the platform limits while writing it: a 20-second execution timeout, and a cap of 10 API calls per execution (excluding api.log()) — design the node to do one signing/calling job, not a multi-step workflow.
  5. Test locally using Cognigy's extension dev/test workflow before uploading anything.
  6. Upload it via Manage → Extensions → Upload, or the Cognigy CLI.
  7. Use it like any built-in node — it now appears in the Flow editor's node palette; add it inside a tool branch exactly like httpRequest or code.
Reach for this only when the same logic is genuinely needed in 3+ tools or projects — for a one-off, a Code node inside the tool that needs it is simpler and faster to change.

10 · portability

Package Export

Bundles the LLM connection and the tools built here so a brand-new project starts from an import, not from zero.

The next time a new client wants "an Aquila-like agent" for a different corpus, this is the difference between reconfiguring an LLM connection and rebuilding every utility tool from scratch versus importing a package and customizing the persona.

  1. Go to Build → Packages (or the export action on the specific resources) in the Aquila project.
  2. Select what to export — at minimum the LLM connection (gpt-4.1-mini, connection 88e50803-f24b-4048-a83f-cc754192f766) and whichever tools from this registry should travel with it.
  3. Export as a .zip.
  4. In the new project: Manage → Packages → Import, and upload the zip.
  5. Reassign the imported LLM connection as the new AI Agent's provider, in its Job Selection / llmProviderReferenceId setting.
  6. Regenerate any Webhook Endpoint API keys. Those specifically do not survive export/import — a documented restriction, not an oversight — so generate a fresh key in the target project and update whatever calls it.
