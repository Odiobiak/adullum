Why this shape

The decisions that constrain everything downstream.

Adullum answers Bible questions with citations, not vibes. Three decisions came before any code, because reversing them later would mean rewriting most of the app:

  • Supabase for storage, not a standalone vector DB. A mobile app needs auth and a relational DB anyway. Postgres + pgvector means the Bible corpus, its embeddings, and future user data (accounts, saved studies, chat history) live in one instance instead of syncing two systems.
  • Hybrid retrieval, not pure vector search. "John 3:16" and "what does propitiation mean" both fail badly under pure semantic search — the first needs exact lookup, the second needs exact words. Vector search is the generalist, not the only tool.
  • A verify step is not optional. A hallucinated Bible verse is worse than a wrong answer almost anywhere else in RAG — it's specifically the kind of error that erodes trust in the whole app. ground_check exists because synthesize is not trusted to grade its own work.
Licensing constraint Only public-domain translations (KJV, ASV, WEB, BSB) are ingested. NIV/ESV/NASB are copyrighted — bundling them in an open GitHub repo isn't viable without a commercial license.

Architecture

One graph, one state shape, three kinds of client.

The FastAPI layer is a thin shell around the LangGraph agent — it exists so the agent never has to know whether it's being called by a browser, a future voice pipeline, or a future mobile app. All three talk to the same /chat contract.

The retry edge out of ground_check is the one piece of real control flow in the graph: on the first failure it loops back to retrieve with a wider result set (k goes from 8 to 14), on the theory that the answer wasn't grounded because the right verse wasn't in context yet — not because the model is confused. It gives up after one retry (MAX_RETRIES = 1 in app/agent/nodes.py) rather than looping indefinitely.

Build log

What got built, in order, and why it's shaped that way.

  • 1 · Config & Supabase client

    config.py · db.py · schemas.py

    One Settings object read once at import time (fails fast on missing env vars), one cached Supabase client, one set of shared pydantic models so retrieval, agent state, and API responses all agree on what a Verse looks like.

  • 2 · Hybrid retrieval

    retrieval.py

    A reference-regex parser with a book-alias table, cosine similarity via a match_verses Postgres RPC, and full-text search over a generated tsvector column — merged and deduped, reference hits first.

  • 3 · LangGraph agent

    agent/state.py · nodes.py · graph.py

    Five explicit nodes rather than one ReAct loop, so the generate-then-verify pattern (synthesize → ground_check) is visible in the graph shape itself, not buried in a prompt.

  • 4 · FastAPI service

    main.py

    Same graph behind two endpoints: /chat for a simple request/response, /chat/stream emitting SSE per-node-progress — the shape a future voice or mobile client actually needs, proven out today by the plain web client.

  • 5 · Ingest script

    scripts/ingest.py

    Reads a flat verse JSON, attaches book order/testament/genre from a canonical 66-book table, embeds and upserts in batches so a translation (~31k verses) doesn't go through as one request.

  • 6 · SSE test client

    web/index.html

    No framework, no build step — a hand-rolled SSE reader (the browser's EventSource can't send a POST body, and /chat/stream needs one) proves the streaming contract works before any real front-end is built against it.

  • 7 · Documentation pass

    docstrings throughout app/

    Every public function got a docstring explaining the "why," not just the "what" — the goal being that picking this repo back up in six months doesn't require reconstructing the reasoning from scratch.

  • 8 · This document

    docs/build-process.html

    The reference this whole log is written into.

Running it

First run, end to end, from an empty Supabase project.

  1. Create the Supabase project and load the schema

    Create a free project at supabase.com. In the SQL editor, paste and run supabase/schema.sql in full — it enables pgvector, creates the verses table, the match_verses similarity-search function, and the chat_sessions/chat_messages tables with row-level security already scoped to auth.uid().

  2. Configure environment

    Copy .env.example to .env. Fill in SUPABASE_URL and SUPABASE_SERVICE_KEY from Project Settings → API (use the service_role key — this app runs server-side only), plus OPENAI_API_KEY.

    cp .env.example .env

  3. Install dependencies

    cd adullum
python3 -m venv .venv && source .venv/bin/activate
pip install -e .

  4. Get a public-domain translation as JSON

    The ingest script expects a flat JSON array: [{"book": "Genesis", "chapter": 1, "verse": 1, "text": "..."}, ...]. The Berean Standard Bible (bereanbible.com/bsb.json) and scrollmapper's bible_databases repo on GitHub both offer public-domain translations in easily-reshaped formats. Save the file as data/bsb.json.

  5. Ingest

    python scripts/ingest.py --file data/bsb.json --translation BSB

    Embeds and upserts in batches of 200, printing progress as it goes. For a single translation this is a one-time cost — re-running it is safe and idempotent (upsert on the translation, book, chapter, verse unique key).

  6. Rebuild the vector index against real data

    schema.sql creates the ivfflat index before any rows exist, so its cluster centers are picked blind. Once the corpus is loaded, reindexing lets pgvector pick centers from the actual embedding distribution — meaningfully better recall for the same query cost.

    -- in the Supabase SQL editor
reindex index verses_embedding_idx;

  7. Run the API

    uvicorn app.main:app --reload

    Serves on http://localhost:8000. Check /health returns {"status": "ok"} before moving on.

  8. Open the test client

    Open web/index.html directly in a browser (or serve it — either works, CORS is wide open for local dev). Confirm the API field reads http://localhost:8000 and Translation matches what you ingested, then ask a question. You should see step pills light up (classifying → retrieving verses → drafting answer → checking grounding → citing), the answer appear, then citation tags.

    # optional — only if the browser blocks file:// fetches
cd web && python3 -m http.server 5500

Next steps

Concrete direction for each, not just a wish list.

Schema ready, not wired up

Auth + persisted history

Supabase Auth on a real frontend (magic link or OAuth) issues a JWT. The API needs a second Supabase client construction — today's get_supabase() always uses the service-role key, which bypasses RLS entirely. Authenticated writes need a per-request client built with the user's JWT so chat_sessions/ chat_messages' RLS policies actually apply.

Not started

Voice front-end

STT → /chat/stream → TTS. The current stream emits the full answer as one SSE event, which is fine for text but too coarse for speech — real-time TTS wants token-level streaming. Swap synthesize's single _llm.invoke for astream_events, emit an answer_token SSE event per token, and let the TTS layer start speaking before the full answer lands.

Not started

Mobile client (Expo)

Same contract, new client: fetch + ReadableStream against /chat/stream, mirroring exactly what web/index.html does today. Requires narrowing CORS from allow_origins=["*"] to the app's real origin before shipping, plus Supabase Auth session persistence via AsyncStorage.

Not started

Evaluation harness

A fixed set of 30–50 Q&A pairs with expected citations — deliberately including a few doctrinally disputed questions to check the "range of interpretation" behavior actually fires. Run nightly, score citation precision/recall, and pipe traces through LangSmith or Langfuse to see exactly which queries trigger a ground_check retry — the strongest signal for whether k or the synthesize prompt need tuning.

Partially supported

Multi-translation compare

The schema's translation column and unique constraint already support more than one translation side by side — ingesting a second one (e.g. WEB) is just running ingest.py again with a different --translation. What's missing is purely client-side: a toggle or side-by-side view, since hybrid_retrieve already takes translation as a parameter.
