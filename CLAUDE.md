# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Adullam is a Bible study agent named Aquila: ask a Scripture question, get a grounded answer with chapter-and-verse citations, never an invented reference. Built as a learning project (LangGraph + Supabase + FastAPI) designed to grow: chat today, voice and mobile later.

## Commands

```bash
pip install -e ".[dev]"                                  # install app + dev deps
uvicorn app.main:app --reload --reload-dir app --reload-dir web   # one process: REST API, SSE, MCP server, and the web UI all at :8000
                                                          # (--reload-dir keeps OneDrive syncing .venv from restarting the server mid-request)
python scripts/fetch_translation.py --translation KJV   # download KJV/ASV/WEB/BSB to data/kjv.json in the shape ingest.py reads
python scripts/ingest.py --file data/bsb.json --translation BSB   # load a translation into Supabase; only BSB (the search translation) is embedded, the rest go in as text
python scripts/ingest_cross_references.py                # load classic cross-references for Connections (after its migration); downloads the data if needed
python scripts/set_password.py someone@example.com      # set or reset an account's password from the terminal (prompts for it, never echoes)
python scripts/make_vapid_keys.py                        # make the key pair that signs push notifications; put both lines in .env and on Render
python scripts/set_supporter.py someone@example.com     # mark a monthly giver as a friend of the cave (--remove when they stop)
pytest                                                    # run the test suite (tests/)
```

Config lives in `.env`, read once into `app/config.py::settings`. `tests/conftest.py` sets dummy Supabase/OpenAI credentials so the suite runs without a real `.env` (in CI, in particular); the suite itself only covers pure logic (`app/retrieval.py`'s parsers, `app/schemas.py`, the graph's routing functions) and the API contract with the compiled `agent` mocked out in `tests/test_api.py`. Nothing in it makes a real LLM or Supabase call. `.github/workflows/test.yml` runs it on every push and PR.

## Architecture

One FastAPI process (`app/main.py`) serves three things off the same LangGraph agent, so there is exactly one place Aquila's behavior is defined:
- `POST /chat` and `POST /chat/stream` for the web client
- `/mcp/sse`, an MCP server (`app/mcp_server.py`) exposing an `ask_aquila` tool, meant for Cognigy's MCP Tool Node or any other MCP client
- `web/index.html` mounted as static files at `/`, so a single deploy needs no separate frontend host

### The agent graph

`app/agent/graph.py` wires the nodes in `app/agent/nodes.py` using the state in `app/agent/state.py`:

```
(mode="listen") --> listen --> END                      Refuge's Aquila, see below
(mode="pray")   --> pray_with --> END                   Pray with Aquila, see below

classify_intent --meta--> answer_meta --> END
       |
     other
       v
   retrieve --> synthesize --> ground_check --ungrounded, retries left--> retrieve (wider k)
                                     |
                                grounded, or retries exhausted
                                     v
                              format_citations --> suggest_followups --> END
```

`suggest_followups` (two questions, `nodes.py::FOLLOWUP_COUNT`) runs last deliberately: the answer and citations have already
streamed to the client by then, so its extra LLM call costs no perceived latency.
It is also non-fatal, returning an empty list on failure rather than sinking an
answer that was otherwise complete and grounded.

`pray_with` is "Pray with Aquila" on the prayer list (`web/prayers.js` sends
`mode: "pray"` to `/chat/stream`): three parts under their own headings
(`## Scripture to hold onto`, `## A prayer`, `## Keep praying`), no study and no
follow-ups. It uses the same reference check as `listen` below, rewriting once
and then praying without Scripture rather than quoting an unlisted verse.

`listen` is the same Aquila in Refuge (`app/refuge.py` sets `mode="listen"` and the
whole talk as `history`): no headings, no follow-ups, one gentle reply. It still
never invents a verse. It looks verses up only when Scripture is wanted, and
`unlisted_references` checks every reference in the reply against what was looked
up, rewriting once and then dropping Scripture altogether. A care check (the model,
plus the phrases in `app/care.py`, which always count) sets `care`, and the client
shows helplines under the reply. Keep `LISTEN_SYSTEM_PROMPT`'s house-style line if
you touch it.

### The shape of an answer

`SYNTHESIZE_SYSTEM_PROMPT` asks for three Markdown headings (`## The passage`,
`## Context`, `## To think about`), which the web client renders as ruled section
headings and `suggest_followups` extends with a "Keep going" block.

**Fact is stated; meaning is offered.** This is the product's stance, not a style
choice: Aquila is a place to rest and learn, never one that presses a meaning on
anyone. What the text says and what the verses themselves show (who speaks, to
whom, what happens) goes in "The passage" and "Context", plainly and cited.
Every reading of a passage (what it means, teaches or asks of someone) goes only
in "To think about", offered as threads to consider and ending with a question,
never as a conclusion ("this means", "this teaches us" are out). There was a
"What it means" heading once; it was removed for exactly this reason, so don't
bring it back. `GROUND_CHECK_PROMPT` knows a reflection offered as a question is
not a claim, while an interpretation stated as fact still has to be supported.

Under each answer stay two quiet lines and nothing more: the references as plain
links (they open Connections), then Bible, Connections, Save, and Listen and
Share as icons (`cave.js::decorateAnswer`). Save is one tap into Saved in the Bible (a second tap takes it back out). The "Close to..." strip of related
verses was removed, since Connections already shows them.
Two things depend on that format, so changing the headings means changing both:
`web/index.html::renderAnswerHtml` (which strips the surrounding newlines so the
Markdown's blank lines don't stack on top of the heading's own margin) and
`app/mcp_server.py::_spoken` (which turns the headings back into sayable
sentences, since a voice gateway reads the tool's answer string verbatim and
would otherwise pronounce the hashes).

The `meta` intent exists because `synthesize` is hard-instructed to answer only from retrieved verses. Before this branch existed, a question like "what's your name?" would retrieve unrelated verses about names and Aquila would dodge the question instead of just answering as herself. Anything that is not actually a Bible-content question should route here, not through retrieval.

### Retrieval (`app/retrieval.py`)

`hybrid_retrieve` tries three paths and merges/dedupes the results, reference hits first:
1. **Reference regex** (`parse_reference`) for a book name immediately followed by a chapter number.
2. **Book-of-X detection** (`parse_book_mention`) for a book named with no chapter (e.g. "the Book of James"), which pulls that book's opening verses directly rather than letting a book-overview question drift across the whole corpus via unscoped vector search. Deliberately narrow (`book of X` phrasing only, not any bare book name), because several book names (Job, Mark, Acts, Titus, James, John, Ruth) are also common English words and would false-positive on unrelated questions.
3. **Vector search** via the `match_verses` Postgres RPC (`supabase/schema.sql`), and **keyword search** over a generated `tsvector` column, topping up whatever the first two didn't fill.

Embeddings are kept small on purpose, because a 1536-dimension vector on every verse of four translations once filled the 2 GB disk and put the project in read-only mode (`supabase/migrations/20261108_compact_embeddings.sql` explains and fixes it; run it once, after the others):
- **Only `settings.search_translation` (BSB) is embedded.** `match_verses` finds the nearest BSB verses and returns the same book, chapter and verse from the requested translation, so every translation still gets semantic search. `scripts/ingest.py` stores the others as text only. Changing the search translation means re-ingesting the new one with embeddings and updating the `'BSB'` in that migration.
- **512 dimensions at half precision** (`halfvec(512)`), about 1 KB a verse. `embed_query` and the ingest both ask OpenAI for `dimensions=settings.embedding_dim`; `text-embedding-3` models are built so that this matches shortening a full embedding and rescaling it, which is how the migration converted the stored ones without re-embedding. Verse search and memories (`user_memories`) share `embed_query`, so they must stay the same size.
- **The index is HNSW**, which keeps itself current as rows are added. There is no rebuild step after an ingest.

### Observability (`app/observability.py`)

Langfuse SDK v4. The module docstring documents three non-obvious failure modes already hit and fixed once, read it before touching this file:
- `os.environ` must actually have `LANGFUSE_*` set (pydantic-settings reads `.env` into its own object without touching `os.environ`; the Langfuse SDK reads `os.environ` directly). `load_dotenv()` in `app/config.py` handles this.
- The per-request `CallbackHandler` must never be cached or shared across requests. It exposes the trace it created via the plain instance attribute `last_trace_id`, and sharing one instance would race that attribute across concurrent requests.
- Scoring a trace from inside a node function must use that explicit `last_trace_id`, not Langfuse's ambient "current trace" context. LangGraph runs sync node functions on a worker thread that does not inherit the main coroutine's contextvars, so the ambient lookup fails there.

### The cave: accounts, journal, plans, memory (`app/auth.py`, `app/cave.py`, `app/reading_plans.py`, `app/memory.py`, `web/cave.js`)

Run the files in `supabase/migrations/` once each, in date order, in the Supabase SQL editor (`20261104_my_cave.sql`, `20261105_hearth.sql`, `20261106_plan_titles.sql`, and on through `20261122_amens_wall_views.sql`). Until the first runs, `/me/*` returns a 503 that says so and chat quietly runs as a guest; until the second, the home screen hides its embers and "Mark as read" explains what to run; until the third, plans shaped with Aquila save without their title and show a generic one.
- **Auth is brokered by this server.** The browser never holds a Supabase key. `/auth/*` signs people in on a throwaway client from `app/auth.py::_auth_client` (never the shared `get_supabase()` one, which a sign-in would switch to that user's token), using the implicit flow so magic-link tokens land in the URL fragment for `web/cave.js` to pick up. Magic links only return here if the site URL is listed under Supabase Auth > URL Configuration; otherwise Supabase sends them to its Site URL (once left as the default `http://localhost:3000`, which broke every production link). On Render the redirect is https only because `render.yaml` starts uvicorn with `--proxy-headers --forwarded-allow-ips '*'`.
- **Every `/me` query filters by `user_id` in code**, because the service-role client bypasses RLS. The RLS policies in the migration exist for a future client talking to Supabase directly.
- **The home screen is one request.** `GET /me/home` (`app/hearth.py`) gathers embers, the last conversation, today's plan reading, the prayer list at a glance (with `prayed_today` and `for_today`, one open request named each day), a fast underway (`fast_underway`), the person's active habits and a goal due within two weeks (`goal_coming_up`) from Pebbles, a glance at the Amens wall, a journal entry to revisit, an answered prayer at least two weeks old to look back on (`prayers.py::answered_to_remember`) and two memories (the screen doesn't show the memories; they live in Settings), each part failing to null on its own. **Every part runs at the same time** through `app/db.py::gather`, since each query is its own round trip to Supabase and run one after another they once took seconds; keep new parts in that `parts` dict rather than calling them in sequence, and use `gather` anywhere a screen needs several independent queries (`/me`, the Amens wall and its home glance, Pebbles already do). Days are the browser's local days (it sends `today`, checked by `app/days.py::parse_today`), so a streak doesn't break at a UTC midnight.
- **The home screen stays quiet** (`cave.js::showHome`). Top to bottom: a warm opening (`.home-hero`, the cave's arch faint in its corner) with the date and the streak as a few quiet words (a tap shows the week), the greeting and the ask box (a round send button that stays quiet until something is typed), and beside them (under them on a phone) the verse for today (`verseCard`, drawn without a card of its own; Reflect, everything else in "⋯"); then a church live as one full-width line (`homeNote`) only while it's live, Amens and Declare as two cards side by side (Amens only when there's something to tell, Declare then taking the row), then Today (`todayCard`: the plan's reading with a thin bar of how far through it is, Pray with the day's request named, a fast underway as "Day 2 of 21", up to three habits with this week as dots and a goal coming due, the ticks a circle each and a ring in its head that fills as they're done, "Start a reading plan" when there's none) and the last conversation under it, with Look back (`lookBackCard`: a journal entry and an answered prayer, whichever there are) and Support in the side column, so the two columns end close together. A part with nothing to say isn't drawn. The last home is kept on the device for the day (`readHome`/`keepHome`, memories left out) and drawn at once while the fresh one loads; signing out clears it (`writeSession(null)`), a tick forgets it, and the Privacy page says so. Someone new sees "Where would you like to start?" under the greeting (`cave.js::startCard`): six places as small rows, each ticked once they've been (from the home payload, `profile.joined` included, or a tap remembered on the device), gone after three weeks, once all are ticked or when they close it. Keep anything new to a row in an existing list rather than a new card, and keep pills off this page.
- **Verse text on screen always comes from the database.** The verse of the day (`app/hearth.py::VERSES_OF_THE_DAY`), the welcome page's example passage and the signed-out page's verse are fetched through `/verse-of-the-day` and `/verse`, never typed into the page. The only hard-coded quotation is the KJV 1 Samuel 22 passage that explains the name (on sign in and the welcome page's "Why Adullam"), and it is labelled KJV. The welcome page is kept short: one line under the headline, the ask box with its starting questions as one quiet "Try" line (never pills), the example answer, then "Made for the moments that matter": the four things Adullam does best after Aquila (whom the hero already shows), in this order: Amens across the page (the wall as people see it: a request, good news, a kind word back, and its plain facts), the cave as a phone open on Refuge (`.cave-feature`, its rooms drawn as `refuge.js::threshold` draws them, so keep the two in step), then sermon notes and Declare ("When you don't have the words") side by side, in a row that swipes on a phone, then a promise card: "Private by design" (Refuge yours alone, a talk there gone unless kept and never remembered, Amens never carrying a name, nobody's data sold; each line must stay true of the code) beside "Free, with no ads" (kept going by people who give), then "And everything else, in one place": a tour with four tabs (Study, Prayer list with Pray with Aquila, Church with going live and Listen, Reflect) holding only what the highlights don't already say, each a one-line promise, three short features and a small made-up example of it in use (references and invented names only, never verse text). Every part of the app belongs in one of those tabs, so keep them in step when a part is added or renamed. Then Why Adullam.
- **Plans shaped with Aquila can't invent a chapter.** `POST /me/plans/build` asks the model only for books and chapter ranges (`app/plan.py::PlanDraft`). `expand_sections` resolves every book through `app/retrieval.py::canonical_book`, clamps ranges to `BOOK_CHAPTER_COUNTS`, and the split into days is the same arithmetic as the whole-Bible plan. Keep the model out of the day-by-day layout.
- **Memory is never Scripture.** `app/memory.py::recall` hands the graph `memories` for signed-in people; `synthesize`, `answer_meta` and `ground_check` all label them as notes about the person that can't support a claim about the Bible. Keep that labelling if you touch those prompts. Note-taking (`remember_turn`) runs after the answer is delivered and is non-fatal, like `suggest_followups`.

### Your account: export, deletion, privacy (`app/account.py`, `docs/incident-response.md`)

- **`GET /me/export`** is one zip: a JSON file per table in `account.py::EXPORT_TABLES`, the chat messages, the profile and the sermon photos. Add any new table that holds what a person keeps to `EXPORT_TABLES`, and give it `user_id ... references auth.users(id) on delete cascade` so deletion reaches it.
- **`DELETE /me`** closes the account once the person types their email. Deleting the auth user cascades to every personal table; reading plans (`on delete set null`) and sermon photos in storage don't cascade, so they're gathered first and removed after the account is gone. `auth.forget_user` drops cached tokens so a closed account stops working at once.
- **Privacy and Terms** are static views in `index.html` (`#privacy`, `#terms`), linked from the welcome footer, sign in and Settings. Every line must stay true of the code: when a feature sends data somewhere new (a provider, a log), the Privacy page changes with it. Bracketed parts are for the operator to fill in.
- **Admin rights need a confirmed email** (`AuthUser.email_confirmed`), since they go by address.
- **Third-party scripts** run with access to the sign-in tokens in localStorage, so load one only when its feature is used (the voice widget waits for a call to start).

### Declare (`app/declare.py`, `web/declare.js`)

Scripture spoken aloud, in faith, over something a person is facing: they say what it is and get an opening line ("In the name of Jesus, I declare God's word over..."), three to five lines to say aloud, each with the verse it rests on, and Amen. `#declare` is the page, `#declare/<id>` a kept one. Three ways in: the home screen's one line (for oneself, its explanation behind an info button), "Declare over it" in an opened prayer (which shows the kept one instead once there is one), and "Declare" in the Prayers tab's New menu (`cave.js::newPrayerMenu`, for something right now, with an optional name). Run `supabase/migrations/20261119_declarations.sql` once, after the others; until then the words still come and Keep says what to run.
- **Aquila only picks references.** `nodes.py::suggest_declare_refs` names passages (one verse or a run of up to three), an ordinary `hybrid_retrieve` runs beside it, and every verse's words are read from the verses table. `nodes.py::write_declaration` writes the lines from those passages, and `declare.py::usable_lines` keeps a line only when its reference is one she was given and its words name none of their own; too few survive and she writes again once, none and the person is asked to put it another way. Kept declarations store each line's words and reference, never verse text. Not a graph node: two structured calls, the first run alongside the search, about five seconds in all.
- **What a line may say**: what its own passage says, with its conditions kept ("as I walk with the Lord"), present tense, "I" for oneself and "you" over someone else. Never "God told me", never a promised outcome ("you will get the job"). Keep those rules in `DECLARE_SYSTEM_PROMPT`.
- **Private and personal.** No sharing, nothing reaches `user_memories`, and every query filters by `user_id`. A declaration over a prayer is kept with it (one per prayer, deleted with it); a quick one becomes a prayer when kept; one for oneself is listed under the form. A situation that sounds unsafe (`care.py::sounds_unsafe`) gets helplines and Refuge instead of words (`refuge.js::helplineRows`).
- **Make it yours** (`declare.js::renderEditor`, `PATCH /me/declarations/{id}`): the person can reword the name, the opening and any line, or drop a line, before or after keeping it. Each line keeps the verse it was given, shown under it while they edit; `declare.py::kept_lines` refuses a reference typed into the words, and the edit route refuses a passage the declaration wasn't given. Share (in "⋯") hands the words and verses to the phone's share sheet, or copies them.
- "Speak it aloud" is full screen (the browser's own where allowed), one line at a time: tap the words or swipe to move on, swipe back to go back. After Amen it rests on a closing screen with "Say it again". The screen is kept awake where the browser allows. There's no read-aloud voice yet: good speech costs money, and the device's built-in voices are the free option if it's ever wanted.

### Refuge and the admin desk (`app/refuge.py`, `app/one_another.py`, `app/care.py`, `web/refuge.js`)

A quiet room in the cave for every kind of season, not only hard ones. Run `supabase/migrations/20261110_refuge.sql` once, after the others; until then the tab shows the setup message. The opening screen (`refuge.js::threshold`) is kept short: "Private to you" with what Refuge is behind its info button, the rooms as tiles of icon and name only (`tile`; Talk with Aquila the wide one, and what came back from Amens a count on its tile), "Talk to a person" always in view, then today's habits as chips and what's been kept. Don't put sentences back under the tiles; each room explains itself behind its own info button. Five rooms, drawn in place inside the tab (not hash routes, so Refuge is one history entry and Back never leads from one room into another):
- **Write it out**: a blank page or a guided shape (lament, thanks, hoping). "Let it go" never touches the server; only "Keep it" stores anything (`refuge_writings`). "Make it a goal" turns a hope into a Pebbles goal, its first small step as the goal's first step. "A nudge" offers a blank page one question at a time (`NUDGES`), Focus fills the screen with the page alone, and leaving with words written asks first, since they can't be brought back.
- **Talk with Aquila**: the graph's `listen` node through `POST /me/refuge/talk`. The browser holds the talk, and it vanishes when the person leaves Refuge (`Refuge.hide`, called by `cave.js` on any other tab or view) unless they press Keep (`refuge_talks`). These runs pass `callbacks: []`, so they are never traced to Langfuse, and nothing here reaches `user_memories`. Keep both true. "Talk out loud" beside Send (`refuge.js::talkRoom`, opening `index.html::openVoice` through `AdullamApp`) is the only way into the voice call; the home, Aquila and the welcome page don't offer it. Because of that, `app/mcp_server.py::ask_aquila` passes `callbacks: []` too, so a voice call keeps Refuge's promise. If voice is ever offered outside Refuge again, decide tracing per caller rather than tracing these. Keep it that way.
- **Pebbles** (once "Grow"; the code still says seeds): goals and habits, in `refuge_seeds` and `refuge_checkins` (`20261112_pebbles_and_prayer_practice.sql` added the columns below, moved the old prayer pebbles onto the prayer list and turned hopes into goals). Each card shows one next action and keeps the rest in a "⋯" menu (`cave.js::moreMenu`). A habit's tick shows at once and the row is redrawn from the server either way; a step can be added right on its goal's card. Praying and fasting belong on the prayer list, not here.

A breath prayer's words are never typed in: each is a reference read from the database in the open translation and cut in two by `breathHalves`, the first half on the breath in and the second on the breath out. Nothing reaches the server; the choices and this week's count stay in the browser's storage.
- **Amens** (first called "One another", which `app/one_another.py` and the `refuge_*` tables still say): share a burden or good news without a name. The two kinds are named as the ask they are, "Pray for me" and "Rejoice with me" (`refuge.js::POST_KINDS`), chosen in a compact composer that opens when tapped, and the info button beside the room's title opens "How Amens works" (`refuge.js::HOW_AMENS_WORKS`); keep that in step if the wall's rules change. The wall is three views under one line that says how much of it the person has stood with ("9 still to pray for", "You've stood with 5 of 14 on the wall", with a bar; `refuge.js::amensRoom`): **To pray for**, a card per post by someone else they haven't answered (`carryCard`, from `amens_to_carry`); **Prayed**, what they've said amen to that's still up, newest amen first (`carriedRow`, from `amens_carried`); and **Yours**, their own posts with where each stands ("On the wall · 9 days left", "Waiting for approval", "Off the wall", "Answered") and what came back (`mineRow`), the evening-note switch at its foot. Run `supabase/migrations/20261122_amens_wall_views.sql` once, after the others; until then the wall says what to run. Saying amen is the one reaction, one count per person on the server, but on screen it reads as what it means (`refuge.js::REACTIONS`): a burden's button is "Say a prayer" and good news's "Rejoice with them", and once pressed either turns to "Amen" with "You and 4 others prayed for this" beneath. "Show more" sends `skip`, the unprayed cards it holds, since praying moves posts out of the view. Tapping one of their own posts opens it in a sheet (`mineCard`), where they see what came back as people ("12 people prayed for you") with anonymous faces, never who, and a post's count is its amens. A post goes through `one_another.screen` (contact details refused; signs of risk are not posted and the writer is shown helplines; OpenAI moderation refuses hate, harassment, sexual and illicit content, while violence goes to a person since it also catches someone describing harm done to them), then goes up straight away when the check flagged nothing and ran (`one_another.goes_up_now`), or waits as `pending` on the **admin desk** (`#desk`, `/admin/refuge`) until someone in `ADMIN_EMAILS` approves it; `AMENS_AUTO_APPROVE=false` sends every post to the desk. A report takes it off the wall at once and back to the desk, for up to `one_another.REPORT_TAKEDOWNS_PER_DAY` reports per person a day and only on a person's first report of that post; past that the post stays up and waits on the desk as "Reported, still up" (`desk.py::_still_up`), so one account can't empty the wall. The reporter is told the same either way.
- **The wall at scale** (`supabase/migrations/20261116_amens_at_scale.sql`; until it runs, the wall says what to run). No followers and no feeds: each person's wall is the database function `amens_to_carry`, posts by others still up that they haven't said amen to, those with the fewest amens first, in a shuffle seeded by who's looking, a page at a time ("Show more"), so prayer spreads across every request. Counts live on the post (`amen_count`, `kind_word_count`, kept by triggers) and amens per day in `refuge_amen_days`; never count amens by loading their rows, since an answer stops at 1,000. The home notice counts posts gone up since the person last opened the wall (`refuge_wall_visits`) that they haven't said amen to. A writer with new amens gets one notification in their evening (`one_another.run_digest`, run by `app/reminders.py`'s loop and its cron route, claimed once per writer by `claim_amens_digest`; `profiles.amens_digest` turns it off from a switch at the foot of Yours, and `profiles.time_zone` is kept by `cave.js::loadProfile`). The database functions are callable by the service role only, since `amens_digest_due` returns who wrote posts.
- **How long a post stays** (`supabase/migrations/20261117_amens_lifetimes.sql`, `one_another.LIFETIME_DAYS`): a prayer request two weeks from when it goes up, which its writer can keep up two weeks more at a time once it's within four days of its end or just past it, up to two months (`kept_up_until`, `POST .../keep-up`, offered by `refuge.js::keepUpNudge` under the share box and on the post); good news a week; a prayer marked answered (`POST .../answered`, with an optional line on how) five more days, shown on the wall as good news and taking good-news kind words. Then it leaves the wall for everyone else (`expires_at`, read by `amens_wall`); the writer's own copy stays, shown "Off the wall". The rules are spelled out once in `refuge.js::HOW_LONG`, shown in "How Amens works" and behind the info button on each of the writer's posts; keep both in step with the server. Others can only say amen, send one of `KIND_WORDS` (verses stored by reference and read from the database), or report. Nobody, the desk included, is ever sent who wrote a post; keep `user_id` out of every wall and desk select.

Helplines live in `web/refuge.js::HELPLINES`, chosen by the browser's region and changeable. Nothing anyone writes, talks through or shares in Refuge appears on the home screen. Two exceptions are deliberate: the person's own active habits (rows in Today, linking to `#pebbles`), and, public, the home's Amens notice (`one_another.py::amens_glance`, drawn by `refuge.js::homeCard`) sits at the top of the home screen as one tappable line, like a notification: how many posts by other people are waiting for this person's amen (a count on the icon) and this week's amens across the whole wall. It opens `#amens`, and it stays hidden when there is nothing to tell. Never put the person's own posts, or anything that shows they posted, on that card.

### The Bible reader, notes and highlights (`app/bible.py`, `app/notes.py`, `app/highlights.py`, `web/reader.js`)

- **A translation is offered only once it's loaded.** `app/bible.py::TRANSLATIONS` lists the public-domain ones (BSB, KJV, WEB, ASV); `/bible/translations` returns the subset that has verses in the database, cached for five minutes, so after ingesting a new one the picker shows it within that window. To add one, fetch it with `scripts/fetch_translation.py` (which normalizes book names and the quirks of each source, listed in its docstring), ingest it, and it appears. It is stored as text only and borrows BSB's embeddings for vector search (see Retrieval above).
- **One translation preference drives everything.** The hidden `#translation` input in `index.html` is the single value Aquila, the verse of the day, Connections and the reader all read. `web/reader.js` sets it from the reader's picker and the one in Settings, remembers it on the device, and saves it to `profiles.preferred_translation` when signed in (applied on the next sign-in via the `adullam:profile` event `cave.js` dispatches).
- **Notes are pinned to book, chapter and verse range, not to a translation**, so a note shows beside the same verse whichever translation is open. `translation` and `verse_text` record what the person was reading when they wrote it. Every `/me/notes` query filters by `user_id`, same rule as the cave.
- **Highlights follow the same rule**, one colour per verse (gold, green, blue, rose), stored a row per verse so overlapping highlights never conflict. The server reads each verse's text from the verses table when it saves one, and `highlights.py::group_highlights` joins neighbouring verses of one colour back into a passage for My notes. The colours are `--hl-*` tokens in all four themes.
- **Asking Aquila about a verse or note is an ordinary question** composed by `reader.js::askQuery` with the reference first (`On John 3:16-18: ...`), so `parse_reference` pulls exactly those verses and nothing in the graph changes. A note goes in quoted as the person's own words; the synthesize prompt still grounds only on retrieved verses, so a note can't become a citation.
- **The Bible tab opens on a front page** (`#bible`, `reader.js::showHub`) with four ways in: Bible (carrying on at the chapter last read on this device), Reading plans, My notes and Saved, so it's plain the tab holds more than the text. Signed in, the last three show how many plans still have today's reading to do, how many notes and highlights are kept and how many things are saved. A bare `#bible` link always lands there; anything that should open a chapter links to one.
- Reader links are `#bible/<Book-with-hyphens>/<chapter>[/<verse>]`; `Reader.href("John 3:16")` builds one. "Bible" under each answer, "Read in context" in the Connections side panel and the chapters under a reading plan's "Today" use it (a plan's chapters open the Bible, not Aquila).

### Sermon notes (`app/sermons.py`, `app/sermon_export.py`, `web/sermons.js`)

Sermon notes are the Sermons part of the Church tab (`#church/sermons`; `#sermons` lands there), drawn by `sermons.js` into `church.js`'s page. Run `supabase/migrations/20261111_sermon_notes.sql` once (it also creates the private `sermon-images` storage bucket). Until then Sermons says what to run.
- **The tab opens on the list.** A note opens only when it's picked (`sermons.js::showList` and `openNote`), then sits beside the list; on a phone it takes the list's place, with "All sermons" to go back.
- **A note is details plus blocks.** Title, speaker, church, date, series and main passage, then an ordered list of blocks (`text`, `heading`, `verse`, `image`, `quote`, `todo`, `link`) stored as JSON and validated by the pydantic models at the top of `app/sermons.py`. The page saves the whole note about a second after each edit.
- **Lists are plain text.** A bullet is a line starting `• `, a numbered item a line starting `1. `. In a text block, Enter carries a list on, Enter on an empty item ends it, `- ` or `* ` at a line's start becomes a bullet, and the block's tools toggle either kind (`sermons.js::toggleList`, `onListKeys`); "List" in the Add bar is a text block that starts with a bullet. Nothing new is stored, so the shared page and PDF and Word exports show them as written, and `sermon_export.markdown_text` turns them into Markdown lists and keeps the line breaks Markdown would otherwise join.
- **The server finds the references, not the page.** Each save runs every block through `retrieval.find_references` and returns `passages` (the whole note, main passage first) and `block_refs` (per block), which the page shows as chips linking to the reader. Verse blocks store only the reference; their text is always read from the database in the reader's translation, on screen and in exports.
- **Photos** are shrunk in the browser to 1600 pixels, sent as base64, checked by their first bytes, and stored under `<user id>/<note id>/` in the `sermon-images` bucket. A block keeps only the path, `clean_blocks` refuses any path outside the note's own folder, and the server signs an hour-long link each time the note is read. Photos dropped from a note, or in a deleted note, are removed from storage. A stored photo path must be a plain file name directly in that folder (`sermons.py::photo_path_ok`), checked again before every download, because the storage library tidies `../` away when it builds a URL.
- **Sharing is a read-only link** (`#sermon/<token>`, `GET /shared/sermons/{token}`, no account needed). `shared_view` strips the user id, storage paths and prayer ids before anything leaves the server, and its photos come through `/shared/sermons/{token}/photos/{index}` rather than a signed link, whose path names the writer's account. Stopping sharing clears the token, so the old link dies for good. Links in a note are kept to http(s) only, since strangers open shared notes.
- **Export**: one note as PDF, Word or Markdown (`GET /me/sermons/{id}/export?format=`), or every note as Markdown plus photos in one zip (`/me/sermons/export.zip`). Layout lives in `app/sermon_export.py`, apart from storage, like `app/pdf.py` for plans.
- **Connections**: a to-do step can go onto the prayer list (its `prayer_id` is kept on the step), "Also in your cave" shows those prayers, journal entries on the note's passages and other sermons on the same books (`GET /me/sermons/{id}/connected`, each part failing to empty on its own), and "Ask Aquila about this sermon" puts the main passage first and quotes the notes as the person's own words, so they can never become a citation.

### Church (`app/churches.py`, `app/church_web.py`, `web/church.js`)

The Church tab (`#church`, nav label "Church", the last phone tab, after Bible; the tabs run Home, Cave, Aquila, Bible, Church) holds three parts in one segmented bar: Churches, Sermons (the sermon notes above) and Listen. Run `supabase/migrations/20261114_churches.sql` once, after the others; until then the tab says what to run, and drafting sermon notes from a link needs it too (it adds `church_id`, `source_url` and `week` to `sermon_notes`).
- **Personal, never social.** A church row belongs to the one person who added it. No following, no counts of who else goes, no directory, nothing suggested, and no giving (a church's page has About, not Give). Keep it that way.
- **Adding a church**: paste a link or enter it by hand. `POST /me/churches/read` reads the page plus up to three likely pages (visit, events, news), its schema.org data and its links, and the model fills `ChurchDraft` from the page text only. `church_web.useful_pages` picks the extra pages best first by kind (times, then events, then about, a hint counting only at the start of a path part), and `site_text` shares the text budget between them with repeated menus left out, so the visit page isn't crowded out by the homepage. YouTube links are found in scripts too (`Page.mentions`), old `youtube.com/<name>` channel links count, and a site linking only a video leads to its channel. A site behind a bot check (Cloudflare's 403) says so, and the page offers "Enter it myself" with the link filled in. Nothing is saved until the person reviews the form and adds it. A church added from a site is read again in the background when it's opened a week or more after `checked_at`; that refresh only replaces events and notices, never gatherings the person may have corrected.
- **Every fetch goes through `church_web.safe_get`**, which follows http(s) to public addresses only, re-checks every redirect hop and caps the size. Never fetch a pasted link any other way.
- **Times**: gatherings are stored in the church's own IANA time zone, `{label, day (0 = Sunday), time "HH:MM"}`, and `church.js::nextAt` shows each in the person's time. Each event and gathering has a bell (Reminders below); an event's bell also offers its own calendar as an .ics file.
- **Notices and the info icon**: each notice keeps when Adullam first saw it (`added`); the icon's count is the notices newer than `notices_seen_at`, cleared by `POST /me/churches/{id}/seen` when the icon or the News tab is opened.
- **Live**: a church's YouTube `/live` page is checked at most every two minutes per channel (no API key: the canonical watch link plus `"isLiveNow":true`). Home shows one notification line (`cave.js::homeNote`) only while a church is live and its "Tell me when it's live" is on, and nothing else about churches; the same switch sends a notification once per stream (see Reminders below). `#church/live/<id>` plays it with notes beside it, kept in the browser until "Save to Sermons".
- **Sermons and Listen** come from each church's YouTube channel (the channel id is found and kept on save) and podcast (Apple Podcasts links resolve to their feed, a show's web page to the feed it names; Spotify has none). YouTube's public feed has been answering 404 for every channel, so `churches._youtube_uploads` falls back to the channel's own Videos and Live pages (`church_web.parse_channel_page`, dated from "2 days ago"). Every sermon carries an ISO `published` date and a `length`. Listen (`app/listen.py`) offers those sermons and Adullam's catalog, a short hand-chosen list of official public sermon podcasts across the traditions (`listen.py::CATALOG`, each feed checked to open and parse; keep it balanced across traditions if you add to it). Each sermon is tagged with seasons (weary, anxious, grateful, grieving, deciding, joyful) by the model once, kept in `sermon_moods`, which holds no personal data; with no season picked every sermon shows and nothing waits on the model; picking one tags a batch before the answer and the rest after it (`pending`, and the page looks again). For speed, `listen.warm` reads and sorts the catalog as the server starts, `church_web.read_podcast_feed` stops reading a feed once its latest episodes are in, and `_cached_feed` answers a kept feed at once while refreshing it behind. The season and the source (everywhere, your churches or one of them, the catalog or one source) are two compact dropdowns on one line, with what Listen is behind the info button; keep pills off this page. Videos play in a docked youtube-nocookie player (`church.js::play`): a corner on a wide screen, the width of a phone above its tab bar, shrinkable to one line while it keeps playing, with the page given room beneath it (`--player-room`). It's placed with left/right, never a transform, since the `rise` animation ends on `transform: none`.
- **Notes from a link** (`POST /me/sermons/from-link`): the video's transcript (youtube-transcript-api, which YouTube often refuses to cloud servers) or else its description, drafted into `SermonDraft`. A podcast episode already read from a feed is drafted from the feed's own title and description (`churches.cached_episode`), since its link is often the audio file or a page that's mostly script; an audio link that isn't is refused gently. `churches.py::note_from_draft` keeps only passages the reference parser accepts, as verse blocks (text read from the database when shown), drops a "quote" that is really a verse, and adds timestamps only when there's a video. The draft is an ordinary sermon note after that.
- **The week after** (`#church/week/<id>`, `week_steps`): reread the main passage, carry a verse (Save puts it in Saved), one question (the answer kept in `week`), do the thing (the note's first to-do), pray. The Churches part shows it as "This week" for a sermon from the last eight days.

### Reminders and push notifications (`app/reminders.py`, `app/push.py`, `web/notify.js`, `web/sw.js`)

Run `supabase/migrations/20261115_reminders.sql` once, after the churches one. Set `VAPID_PUBLIC_KEY` and `VAPID_PRIVATE_KEY` (from `scripts/make_vapid_keys.py`), `VAPID_SUBJECT` (a `mailto:`) and `CRON_SECRET`; left empty, `/push/key` returns null, the bell says notifications aren't set up, and nothing is ever sent.
- **Bells**: an event can remind a day or an hour before (the evening before or that morning when it has no time); a gathering reminds 30 minutes or an hour before, every week. One row per thing in `reminders`, keyed by what it's about, so the same bell changes it rather than adding another. - **A notification only opens a page in Adullam** (`inside_link`: a `#...` route), and `sw.js` checks again before navigating. Keep both.

### Reflections (`app/reflections.py`, `web/reflections.js`)

A guided time with God over a stretch of time, in the Journal. Run `supabase/migrations/20261113_reflections.sql` once, after the others; until then the Journal works as before and starting a reflection says what to run.
- **Any length, any time.** New entry in the Journal is a small menu (`cave.js::newEntryMenu`): a journal entry or a reflection. A reflection looks back on a month, a quarter, a year or a season with the person's own dates, and ahead to the stretch after it. `reflections.py::period_for` picks the stretch that's ending (one just begun gives way to the one before), the start sheet's arrows move it, and `season_period` follows a season with one as long. There is no invitation or prompt to start one; keep it that way. The person can name it as they choose the stretch (`title`) and rename it at the top of the reflection; without a name it's called by its dates.
- **Three stages, saved as they write** (`PUT /me/reflections/{id}`, a second after each change). Look back: a summary folded into one line until it's tapped (the numbers they choose to count, cave counts marked with the cave's arch from `cave_counts` and their own; their goals, from Pebbles and their own; passages; answered prayers as "stones of help"), then the areas of life they pick (Spiritual, Family and so on, or their own), each rated Hard, Mixed, Steady or Thriving with a line on what happened. Lay down. Look ahead mirrors look back: numbers to aim for with last time beside each, and for each area where they'd like it to be and what they'd like to see (a habit, a number, a date, or a hope). A month asks fewer questions.
- **Kept, it's the plan for the stretch ahead.** `POST /me/reflections/{id}/keep` turns each goal marked to track, and each of the person's own numbers to aim for, into a pebble (`refuge_seeds`, the id kept on the goal so it's never planted twice). The current plan is pinned at the top of the Journal (`reflections.js::planCard`: how far through the stretch, each number with a bar, progress from `plan_progress`, then Open and Write about it; it no longer offers praying with Aquila), a kept one in the list says what it set out (`rowCard`), the home screen shows a halfway check-in for two weeks from the middle of any stretch longer than a month (`reflection_glance`, `reflections.js::homeCard`), and the next reflection opens with "What you set out": that plan beside what happened.
- **The verse is a reference only**, its text read from the database. A reference that doesn't parse yet is kept as typed and named in `verse_error`, so it never costs the person the rest of their writing. The word for the year is UI text (Inter), not Scripture.
- **Private, and never memory.** Nothing here reaches `user_memories` or the Amens wall, and every query filters by `user_id` in code.

### Connections, the knowledge graph (`app/connections.py`, `web/graph.js`)

On screen it is "Connections" (it was "Map" at first, which read as a geographic map). The nav item, the door on the Bible's front page and the verse bar all use that name. On phones the tab bar holds Church instead, so the Bible's front page is its way in.

`GET /connections` draws two kinds of link from each seed verse, and every edge says which in `kinds`:
- **Close in meaning** (`"meaning"`, solid lines): the seed's stored embedding (read from the search translation's copy of that verse) fed back through `match_verses` for its nearest neighbours in other chapters. No new SQL and no LLM call.
- **Classic cross-references** (`"cross_ref"`, dashed accent lines): the seed's best-voted rows in `cross_references` (`supabase/migrations/20261111_cross_references.sql`, loaded by `scripts/ingest_cross_references.py`). The data is OpenBible.info's, CC BY, built on the public-domain Treasury of Scripture Knowledge; the licence asks for credit, which the graph's legend and the cross-reference panel give, so keep it. A link to a run of verses is drawn to its first verse and carries the run as `passage`. Until the migration runs the table is simply skipped.
A pair that is both is drawn solid in the accent colour. The legend toggles each kind.

Opened with nothing to show (the nav item, the Bible's door), the graph offers `graph.js::STARTERS`, a few themes each with the passage that starts it; the labels are themes, never quoted verse text. On phones the graph stops above the tab bar, Connections is the lit tab while it's open, and tapping another tab or any route change closes it.

Tapping a line (or "Why?" beside a neighbour in a verse's panel) calls `POST /connections/explain`: `app/agent/nodes.py::explain_link` gives two or three sentences on how the two passages connect, from those two passages only (a reply naming any other verse is rewritten, then replaced by a plain sentence), cached per link with `lru_cache`. `web/graph.js` lazy-loads d3 from cdnjs the first time the graph opens.

A new conversation sits in the middle of the page: Aquila's mark and the question, the text box under them, then four small starters in one row (`index.html::TOPICS` drawn with `data-cards`, an icon and a word each, the whole question as the button's name), placed by CSS while `#askEmpty` shows; once it begins, the composer goes back to the foot as a floating card with a round send arrow, and one line under it says she can make mistakes; "Keep going" offers each next question as a quiet card. "What Aquila remembers" lives in Settings, next to profile and theme. Routes: `#cave`, `#journal`, `#prayers` and `#refuge` open the cave (`#cave` on Refuge, the others on their tab); `#church` is the Church tab, with `#church/sermons`, `#church/listen`, `#church/add`, `#church/c/<id>`, `#church/live/<id>` and `#church/week/<id>` inside it, and `#sermons` lands on its Sermons; `#reflection/<id>` opens a reflection inside the Journal tab; `#sermon/<token>` is a shared sermon note, open to guests; `#amens` and `#pebbles` open Refuge inside that room; `#notes`, `#saved` and `#plans` land on those pages in the Bible (the old `#memorize` lands on Saved); `#conversations` lands on Aquila; `#settings` and `#remembers` open Settings (the second scrolled to memory); `#declare` is Declare and `#declare/<id>` a kept declaration; `#desk` is the admin desk; `#privacy` and `#terms` are open to everyone.

Words: keep screens light to read. A title's explanation goes behind a small info button beside it, not in a paragraph under it: `cave.js::titleInfo` (or `info`, `sheetTitle` for a sheet, `room(title, about)` in Refuge, and `data-info="..."` on a static heading in `index.html`). The popover can carry a "Learn more" that opens a fuller explanation, as Amens does with "How Amens works". Keep on the page what has to be seen at once: safety and helplines, what sharing a link exposes, health cautions, empty states.

Toasts (`cave.js::toast(text, { tone, action })`) are small cards with an icon for their tone: `done` (a tick, the default), `info` for a nudge ("Write a little first.") and `error` for anything that failed (pass it for every `err.message`). An `action` adds one button, kept for going straight to what was just made (`{ label: "View", href: "#bible/saved" }`). They rise from the bottom on a wide screen and drop from the top on a phone, clear of the tab bar and composer; the timing is in JavaScript because reduced motion switches CSS animations off. No flame icons anywhere: what Adullam counts carries the cave's arch, a reflection a sun on the horizon, Aquila's memory a clock turning back.

Type: Inter for the interface and Source Serif 4 only for quoted Scripture (`.scripture`, `.scripture-lg`), so a verse always reads as the text rather than as UI. Labels are sentence case; keep shouted uppercase kickers out.

Size: controls are compact and read their height from the tokens under the themes in `app.css` (`--h-btn`, `--h-btn-sm`, `--h-chip`, `--h-icon`), which grow a little on touch screens (`pointer: coarse`) so tap targets stay comfortable. Give a new button or chip one of those heights rather than a pixel value. Inputs stay at 16px so iOS doesn't zoom on focus. The cave tabs and the sign-in switch are segmented controls (`.tabs`, `.seg`); on a phone the cave's tabs share the full width, and sheets rise from the bottom. The top bar spans the window, and its gutter matches `.wrap` (20px, 16px on a phone) so the logo lines up with the page.

Shape: controls are pills (`--pill`), cards are generously rounded (`--radius`), and warmth comes from soft radial glows built from `--glow`/`--glow-strong` (the welcome preview, warm cards, sign in, signed out) plus the one gradient button, `.btn-ember`, which runs `--ember` into `--ember-hi` over an `--ember-glow` shadow. Build any new glow from those tokens so it follows the theme.

Themes: seven palettes defined only as tokens at the top of `app.css` and set as `<html data-theme>`: Dawn, Lily (clean white), Olive Grove, Twilight and Hearth for everyone, and Almond (light) and Cedar (dark) for friends of the cave (`cave.js::SUPPORTER_THEMES`, unlocked by `cave.js::isFriend`, see Support below). The two supporter themes also switch on a signature layer the free ones leave off: a fixed aura behind the app (`--aura`, painted by `body::before`), gradient page titles (`--title-ink`), a richer gradient on primary buttons (`--ember-grad`, with a `--sheen` along the top), lifted cards (`--lift`, `--card-tint`), a glassier top bar (`--bar-glass`), a still picture behind the app (`--ornament` on `body::after`: Almond's flowering branch, Cedar's stars, grain and ridge of cedars, the ridge dropped on phones), a slow drift on the aura (`--aura-motion`, off under reduced motion), foil-edged feature cards (`--edge`), a gradient on the lit nav item (`--nav-active`), a gradient that slides on button hover (`--grad-size`) and their own text selection (`--select`). Keep ornaments to the corners and edges, never behind the reading column. Their defaults sit in a `:root` block above the themes, which must stay above them since the two tie on specificity. Give any new colour a token in all seven blocks rather than a literal, and check its contrast in the light themes (Dawn, Lily, Olive Grove, Almond), where muted text and the accent are closest to failing.

Two things worth knowing before changing the SSE handling:
- It hand-rolls an SSE reader over `fetch()` because the browser's `EventSource` cannot send a POST body, and `/chat/stream` needs one.
- The server sends CRLF line endings; the client normalizes `\r\n` to `\n` before framing on blank lines. Removing that normalization silently breaks every response (the whole stream gets stuck in an internal buffer and nothing renders, with no error shown).

### Support Adullam (`app/support.py`, `web/support.js`)

Adullam stays free with no ads, and nobody's data is sold; giving pays the bills. `#support` is open to everyone and offers two links, set in `.env` as `SUPPORT_ONCE_URL` and `SUPPORT_MONTHLY_URL` (Stripe Payment Links) with `SUPPORT_MONTHLY_AMOUNT` as the page should say the price. Until they're set the page says giving opens soon, and its buttons are disabled rather than leading nowhere. The server never sees a card.
- **People are pointed there from wherever they'd see it**: "Support Adullam" in the account menu, a "Keep the fire lit" card at the end of the home screen's side column ("Not now" hides it on that device for 30 days, and supporters never see it), a card in Settings, the "Free, with no ads" half of the welcome page's promise card, and a line on the signed-out page.
- **Monthly givers are friends of the cave**: `profiles.supporter_since` (`supabase/migrations/20261112_supporters.sql`), set by `scripts/set_supporter.py` until a Stripe webhook does it. `PATCH /me` never accepts it. The checkout link carries the person's id as `client_reference_id` and their email as `prefilled_email`, so that webhook can find the account.
- **The thank-you is cosmetic only**: an ember on the account chip, "Friend of the cave" in the menu, and the Almond and Cedar themes. Admins (`ADMIN_EMAILS`) count as friends of the cave without giving (`cave.js::isFriend`): they get all of it and are never asked to give. `cave.js::supporterSince` stays the giving date alone, so an admin's thank-you line never names a month they started giving. Never hold back the Bible, Aquila, Refuge, prayers or anything else someone relies on, and never put ads in.

### Daily limits (`app/quota.py`, `app/answer_cache.py`)

Adullam is free and paid for by giving, so whatever costs money is counted. Run `supabase/migrations/20261121_usage_limits.sql` once, after the others; until then nothing is limited.
- **Three checks, cheapest first**: a per-minute burst limit held in the process, then one `use_quota` call that counts the person's day and adds an estimated cost to the whole app's day (`usage_days`, subject `'*'`), refusing past `DAILY_BUDGET_USD`. A refused request is never counted. Every number is a setting in `app/config.py` (`QUOTA_*`, `COST_*_USD`), changeable from `.env`.
- **What counts**: a question (`/chat`, `/chat/stream`, `/declare`, `/me/plans/build`), a Refuge talk message, and a voice call (counted by `POST /me/voice/start` once the call connects; `GET /me/voice` is asked before dialling, and the page hangs up at `VOICE_CALL_MINUTES`). A voice call's questions arrive from Cognigy with no person, so `ask_aquila` counts them toward the budget only. Add any new route that calls the model to one of these kinds.
- **Guests** are counted by a sha256 of their address from `True-Client-IP` or `CF-Connecting-IP`, never the raw address and never the first `X-Forwarded-For` entry, which the caller controls.
- **It fails open**: a database error lets the request through, so the provider's monthly limit is the backstop.
- **Limits are said gently**: a 429's `detail` is shown as it is (`err.gentle` in `index.html::ask`, `err.status` from `cave.js::api`), never as an error to retry. Keep the wording in `quota.LIMIT_MESSAGES` kind.
- **Repeats are free**: a study with no memories replays the stream kept from the first time (`answer_cache`, a day, 256 entries, in memory). A prayer, or anything with memories, is never kept. The Privacy page says both of these; keep it in step.
- **Refuge sends a trimmed talk**: the latest `LISTEN_HISTORY_LIMIT` messages up to `LISTEN_HISTORY_CHARS`, since the whole talk goes with every reply.
- **The MCP server takes a key** once `MCP_SECRET` is set (`main.py::_guard_mcp`, as a Bearer header or `?key=`), checked when the stream opens.

### Deployment

`render.yaml` defines the Render Blueprint; secrets are filled in on Render's dashboard, never committed. That includes `ADMIN_EMAILS` (who can open the admin desk); left empty, posts the automatic check isn't sure of wait with nobody to approve them. `AMENS_AUTO_APPROVE` (default true) lets posts the check is clear about go up straight away. `SUPPORT_ONCE_URL` and `SUPPORT_MONTHLY_URL` are the giving links; left empty, the Support page says giving opens soon. `.github/workflows/deploy-watch.yml` polls the Render API and the live `/health` endpoint, opening (or updating) a GitHub issue only on an actual build/deploy failure or a failing health check, and closing it on recovery, so a healthy deploy produces no noise.

## Product constraints that shape the code

- **Only public-domain translations** (KJV, WEB, ASV, BSB). Licensing a copyrighted translation needs a commercial agreement, not viable for an open repo.
- **Grounding is not optional.** `ground_check` exists because a hallucinated Bible verse is worse than a wrong answer in most other RAG use cases, it erodes trust in the whole app.
- **Denominationally disputed questions** (baptism mode, eschatology, predestination vs. free will) get the range of Christian interpretation, never one tradition's view asserted as the answer. This is a rule inside `SYNTHESIZE_SYSTEM_PROMPT` in `app/agent/nodes.py`, not a separate node, keep it there if you touch that prompt.

## House style: keep Aquila, and this repo, sounding like a person

Aquila's whole purpose is to feel like a warm, present companion, not a script. Never use an em dash, and avoid other stylistic tells that read as obviously AI-generated (the triplet "it's not X, it's Y" construction, excessive hedging, restating the question back before answering it). This applies to:
- Aquila's actual answers: `SYNTHESIZE_SYSTEM_PROMPT` and `META_SYSTEM_PROMPT` in `app/agent/nodes.py` carry this instruction directly, keep it there if you rewrite either prompt.
- Anything Claude Code writes in this repo: commit messages, code comments, this file. Use a comma, a period, or just a new sentence instead of an em dash.
